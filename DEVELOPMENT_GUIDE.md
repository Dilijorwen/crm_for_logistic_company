# Инструкция по разработке Log Company

Эта инструкция обязательна для всех изменений в `packages/plugins/@log-company/`.

## 1. Границы проекта и источник истины

- Единственный корень проекта — `/Users/daniil/log_company`.
- Авторитетные исходники собственных плагинов находятся только в `packages/plugins/@log-company/`.
- `storage/plugins/` содержит установленные runtime-копии. Их нельзя редактировать вручную или использовать как источник изменений.
- `storage/tar/`, `dist/`, `lib/`, `es/` и `esm/` — результаты сборки. Исправление всегда начинается в `src/`.
- `storage/db/`, `storage/minio/`, `storage/uploads/`, `storage/logs/`, `backups/` и `.env` содержат локальные данные или секреты и не должны попадать в Git.
- Версия собственного плагина должна быть совместима с используемой версией NocoBase. Сейчас runtime закреплён на NocoBase `2.0.60`.
- Сначала переиспользуется API, модель данных, UI-компонент или механизм NocoBase. Параллельная реализация допустима только при документированной несовместимости.

## 2. Основные принципы

1. Изменение должно проходить весь необходимый путь: UI → API → application use case → domain → repository/storage adapter → база данных.
2. Бизнес-правила не размещаются в React-компонентах, HTTP actions, хуках ORM, миграциях или SQL.
3. Зависимости направлены внутрь. Внутренний слой ничего не знает о внешнем.
4. Публичные контракты, поля, ресурсы и события сохраняют обратную совместимость, если изменение контракта не является прямой целью задачи.
5. Код должен быть типобезопасным, тестируемым и наблюдаемым. Ошибка не должна теряться в пустом `catch`.
6. Новая абстракция вводится для реальной границы или зависимости, а не ради формального количества слоёв.
7. Существенное изменение существующего модуля постепенно приближает затронутый код к этой инструкции, но не запускает массовый рефакторинг несвязанных частей.

## 3. Onion Architecture для backend

Серверная часть пишется в стиле Onion Architecture, привычном для Java backend. Названия технологий отличаются, но правило зависимостей такое же:

```text
interfaces / infrastructure ──> application ──> domain
              composition root связывает реализации с портами
```

Обратные импорты запрещены. `domain` не импортирует `application`, а `application` не импортирует `interfaces` или `infrastructure`.

### 3.1. Рекомендуемая структура плагина

```text
src/server/
  domain/
    <aggregate>/
      entities/
      value-objects/
      repositories/
      services/
      errors/
  application/
    <feature>/
      commands/
      queries/
      dto/
      ports/
  infrastructure/
    persistence/nocobase/
    storage/minio/
    logging/
  interfaces/
    http/
    events/
    hooks/
  collections/
  migrations/
  composition/
  plugin.ts
```

`collections/` и `migrations/` остаются в ожидаемых NocoBase местах, но архитектурно относятся к infrastructure. Для маленького плагина пустые каталоги не создаются: структура растёт вместе с реальными обязанностями.

### 3.2. Domain

Domain содержит бизнес-смысл и инварианты:

- entities и aggregates;
- value objects для идентификаторов, имён, статусов и других значений с правилами;
- domain services только для правил, которые не принадлежат одной entity;
- domain errors;
- интерфейсы domain repositories, если они описывают работу с агрегатами.

Domain не импортирует `@nocobase/*`, Sequelize, Koa `Context`, MinIO/S3, React, Ant Design и конкретный логгер. В domain нет HTTP-статусов, SQL, JSON структуры ответа и переменных окружения.

Entity должна защищать свои инварианты методами. Не создавайте Java-подобные классы только ради getter/setter: для простого неизменяемого значения достаточно точного TypeScript-типа или value object с фабрикой.

### 3.3. Application

Application оркестрирует сценарии использования:

- один command/query handler или use case соответствует одному пользовательскому действию;
- вход и выход описываются DTO из примитивов и устойчивых типов;
- внешние зависимости представлены портами: repository, object storage, clock, id generator, transaction boundary, notification gateway;
- use case проверяет права на объект, загружает domain-модель, вызывает её поведение и сохраняет результат;
- application не знает о Koa, NocoBase resource manager, Sequelize model и формате MinIO request.

Предпочтительное имя операции — действие: `CreateProcessDocument`, `DeleteProcessFolder`, `ChangeProcessParents`. Для класса use case используется один публичный метод `execute()`.

### 3.4. Infrastructure

Infrastructure реализует порты внутренних слоёв:

- NocoBase/Sequelize repositories;
- SQL queries и транзакции;
- MinIO/S3 client;
- адаптеры логирования, времени и генерации ID;
- преобразование database rows в domain entities и обратно.

SQL всегда параметризован. Динамические имена таблиц и колонок берутся только из закрытого списка приложения. PostgreSQL-специфичное решение явно фиксируется в документации и тестах.

Infrastructure не принимает бизнес-решения. Например, правило «процесс нельзя назначить собственным родителем» принадлежит domain/application, а recursive CTE для поиска потомков — persistence adapter.

### 3.5. Interfaces

Interfaces адаптирует внешний мир к application:

- NocoBase resource actions и pre-action handlers;
- Koa request/response;
- database hooks и application events;
- преобразование и валидация входных данных;
- сопоставление domain/application errors с безопасными HTTP-ответами.

HTTP action должен быть тонким: разобрать запрос, вызвать use case, сформировать ответ. Он не содержит SQL, обходов дерева, правил нумерации или операций с MinIO.

### 3.6. Composition root

`plugin.ts` — composition root. Здесь создаются adapters и use cases, регистрируются actions/hooks и связываются интерфейсы с реализациями. В `plugin.ts` не размещается бизнес-логика.

Зависимости передаются через constructor injection. Не используйте глобальный service locator, изменяемые singleton-объекты или доступ к `plugin` из domain/application.

### 3.7. Транзакции и согласованность

- Граница транзакции соответствует одному use case.
- Несколько связанных изменений БД выполняются в одной транзакции.
- Файловое хранилище и БД не образуют общую транзакцию, поэтому обязательна компенсация: удалить загруженный объект при rollback либо восстановить/повторить операцию через надёжное событие.
- Нельзя сначала безвозвратно удалить объект из MinIO, а затем оставить возможность отката строки БД без компенсации.
- Повторный запрос должен быть безопасным или явно защищён idempotency/unique constraint.

## 4. TypeScript code style

- Форматирование задают `.editorconfig` и `.prettierrc`: два пробела, LF, одинарные кавычки, trailing comma, ширина строки 120.
- Используйте точные типы. `any`, `as any` и неограниченные `Record<string, any>` в новом коде запрещены. На внешней границе используйте `unknown` и type guard/schema validation.
- Один файл имеет одну основную ответственность и, как правило, одну главную экспортируемую сущность.
- Имена полные и предметные: `processRepository`, `draftToken`, `parentProcessId`; не `repo`, `data1`, `obj`.
- Булевы значения начинаются с `is`, `has`, `can`, `should`.
- Используйте guard clauses вместо глубокой вложенности.
- Не создавайте «god service». Если класс одновременно регистрирует API, выполняет SQL, применяет бизнес-правила и форматирует ответы, обязанности нужно разделить по слоям.
- Функция или компонент, который трудно прочитать за один экран, рассматривается как кандидат на декомпозицию. Для React-компонентов ориентир — до 250 строк, для application/infrastructure класса — до 300 строк; превышение требует ясной причины.
- Все promise либо `await`-ятся, либо возвращаются вызывающему коду. Стиль `void someAsyncCall()` для fire-and-forget не используется.
- Пустой `catch` запрещён. Если fallback действительно допустим, обработайте известную ошибку, оставьте диагностический контекст и не скрывайте неожиданные исключения.
- Не оставляйте `TODO`, пустые lifecycle methods, закомментированный код или временные заглушки.
- Константы заменяют magic numbers и повторяющиеся технические строки.
- Комментарий объясняет причину или ограничение, а не пересказывает код.

## 5. NocoBase, данные и миграции

- Перед изменением определите runtime клиента: legacy v1 или FlowEngine/v2. Запрещён импорт `@nocobase/client` из чистого v2-кода.
- Коллекции описываются через NocoBase collection definitions.
- Каждое production-изменение схемы, ограничений, индексов или существующих данных получает новую миграцию. Уже применённые миграции не редактируются.
- DDL и backfill не выполняются в `load()`/`init()` плагина. `load()` регистрирует модуль, а изменение схемы выполняет миграция.
- Миграция учитывает существующие строки, `NULL`, дубликаты, внешние ключи, индексы, rollback/forward-only стратегию и объём данных.
- Деструктивная миграция выполняется поэтапно: добавить совместимую структуру → заполнить данные → переключить код → удалить старое отдельным релизом.
- Фильтры и связи используют фактический `filterTargetKey`, а не предполагают, что ключ всегда равен `id`.
- Прямой SQL допустим в infrastructure adapter или migration, когда repository API недостаточно. Он не должен проникать в domain/application.

## 6. API, ошибки и безопасность

Для каждого action обязательны:

- проверка структуры, типов, размера и допустимых значений входа;
- проверка аутентификации;
- проверка права на конкретную запись, а не только роли `loggedIn`;
- проверка существования связанного объекта;
- устойчивый формат успешного ответа и ошибок;
- корректные статусы `400`, `401`, `403`, `404`, `409`, `422`, `500`;
- server-side logging с correlation/request context без секретов и персональных данных;
- тесты успешного сценария, неверного ввода, отсутствующей записи и недостаточных прав.

Пользователь не получает stack trace, SQL, storage key, токен, внутренний путь или исходное сообщение неизвестного исключения. Domain errors переводятся в публичные ошибки только в interfaces layer.

Нельзя расширять ACL через `allow(resource, '*', 'loggedIn')`, если ресурс связан с объектами, доступ к которым ограничен. Сначала проверяется право пользователя на исходный `customs_processes` и требуемое действие.

## 7. Файлы и MinIO

- Ограничивайте количество файлов, размер одного файла и общий размер запроса.
- Проверяйте MIME type и расширение по allowlist; клиентское значение не считается доверенным.
- Пользовательское имя хранится как metadata, а storage key генерируется сервером и не содержит пути пользователя.
- Защищайтесь от path traversal, управляющих символов, двойных расширений и конфликтов имён.
- Временные файлы удаляются при успехе и при любой ошибке.
- Upload/download/delete проверяют права на процесс и принадлежность файла этому процессу.
- Удаление папки с файлами имеет согласованную transaction/compensation стратегию.
- Ошибка MinIO не должна оставлять строку БД, утверждающую, что отсутствующий объект доступен; rollback БД не должен оставлять бесконтрольный объект.

## 8. Frontend

Для нового функционала используйте feature-oriented структуру:

```text
src/client/features/<feature>/
  api/
  model/
  hooks/
  ui/
  lib/
```

- React-компонент отвечает за представление и пользовательские события; загрузка/нормализация данных выносится в typed API client и hooks.
- Общая логика определения текущего процесса должна быть одной переиспользуемой функцией/hook, а не копироваться между блоками.
- Используйте Ant Design v5 и токены темы NocoBase. Не вводите отдельную палитру без требования дизайна.
- Новый и последующий пользовательский интерфейс Log Company сразу пишется на русском языке. Для него не используется
  i18n и не добавляются параллельные ключи `ru-RU`/`en-US`, если локализация не была отдельно запрошена в задаче.
- Сначала реализуются модульные детали для конструктора NocoBase: коллекции, поля, связи, переиспользуемые блоки и
  отдельные действия. Готовая страница с жёстко заданной компоновкой создаётся только отдельным финальным этапом и
  только по прямому требованию. До этого страницу из предоставленных деталей собирает пользователь в конструкторе.
- Каждый экран имеет loading, empty, error и success state.
- Форма валидируется на клиенте и сервере, блокирует повторную отправку и не теряет введённые данные при исправимой ошибке.
- Интерактивные элементы доступны с клавиатуры и имеют понятные accessible name/ARIA attributes.
- Не используйте `alert`; применяйте NocoBase/Ant Design notification, message или Modal.
- Эффекты очищают timers, observers, subscriptions и interceptors. Axios interceptor, зарегистрированный плагином, должен иметь симметричное удаление при unload/disable или гарантированно регистрироваться один раз.

## 9. Тестирование

Тесты располагаются рядом с кодом в `__tests__` и имеют суффикс `.test.ts`, `.spec.ts`, `.test.tsx` или `.spec.tsx`.

- Domain: быстрые unit-тесты инвариантов без NocoBase и БД.
- Application: unit-тесты use cases с fake/in-memory ports.
- Infrastructure: integration-тесты repositories, SQL, migrations и MinIO adapter.
- Interfaces: API-тесты валидации, HTTP statuses, ACL и object-level permissions.
- Frontend: component/hook tests для loading, empty, error, success, повторной отправки и смены текущей записи.
- E2E: критический пользовательский путь после установки собранного плагина.

Минимальный набор для новой операции: успех, неверный ввод, отсутствующая сущность, недостаточные права, граничное значение, повторная операция и ошибка внешнего сервиса.

Server tests NocoBase запускаются последовательно, потому что параллельный запуск может конфликтовать по общей БД.

## 10. Рабочий процесс изменения

1. Прочитать эту инструкцию и документацию затронутого плагина в `docs/log-company/`.
2. Найти все использования изменяемого API, поля, типа, resource и события.
3. Зафиксировать use case, инварианты, права и границы транзакции.
4. Сначала определить/обновить domain и application contracts, затем adapters и interfaces, после этого UI.
5. Добавить миграцию и тесты, если меняются данные или поведение.
6. Отформатировать и проверить только затронутые файлы, затем выполнить связанные тесты и сборку плагина.
7. Собрать пакет из `packages/plugins/@log-company/<plugin>` и установить его штатным plugin manager. Не копировать исправления напрямую в `storage/plugins/`.
8. Проверить логи, состояние плагина, API и реальный UI-сценарий.
9. Обновить документацию, если изменились установка, конфигурация, переменные окружения, данные или пользовательское поведение.

Базовые команды выполняются из корня проекта:

```bash
corepack yarn eslint --fix <изменённые-файлы>
corepack yarn test <путь-к-тесту> --run --reporter=verbose
corepack yarn build @log-company/plugin-<name>
corepack yarn tar @log-company/plugin-<name>
docker compose config
docker compose ps
```

Dev-инфраструктура запускается отдельно от рабочего runtime:

```bash
docker compose --env-file .env.development.local -f docker-compose.dev.yml up -d
```

## 11. Definition of Done

Изменение завершено только если:

- соблюдено направление зависимостей Onion Architecture;
- нет новых `any`, пустых `catch`, fire-and-forget через `void`, заглушек и захардкоженных секретов;
- проверены object-level permissions и негативные сценарии;
- схема данных изменяется новой безопасной миграцией;
- операции БД и MinIO сохраняют согласованность при ошибке;
- новый пользовательский интерфейс написан на русском языке без i18n, если задача прямо не требует локализации;
- UI имеет loading/empty/error/success states и доступен с клавиатуры;
- добавлены и фактически запущены связанные тесты;
- выполнены lint/format/type/build проверки, доступные в окружении;
- runtime-копия получена сборкой из `src/`, а не ручным редактированием;
- документация отражает фактическое поведение;
- в итоговом отчёте перечислены выполненные команды и реальные ограничения.
