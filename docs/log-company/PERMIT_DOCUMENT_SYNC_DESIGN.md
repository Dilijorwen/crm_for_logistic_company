# Интеграция разрешительных документов с FSA и ЕАЭС

## Изменения модели

Существующая коллекция `permit_documents` остаётся единственной основной сущностью документов. В неё добавляются:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `name` | string, not null | Автоматическое отображаемое название и title-поле коллекции |
| `external_id` | string, nullable | Числовой ID карточки FSA либо UUID карточки ЕАЭС/SWIS |
| `external_status` | string, nullable | Исходный код или текст статуса внешнего реестра |
| `sync_status` | select, not null | `PENDING`, `SUCCESS`, `NOT_FOUND`, `ERROR` |
| `last_checked_at` | datetime, nullable | Время последней завершённой попытки синхронизации |
| `last_sync_error` | text, nullable | Безопасное описание последней ошибки без секретов и stack trace |
| `technical_regulations` | belongsToMany | Связь с единым справочником технических регламентов |

Реестровые поля `status`, `valid_from`, `valid_until` и `product_information` допускают `NULL` во время
`PENDING`, `NOT_FOUND` и `ERROR`. Для `SUCCESS` действуют инварианты:

- `valid_from` и `product_information` обязательны;
- `valid_until` для ДС и СС заполняется, когда реестр указывает срок действия; для документов на единичное изделие
  Росаккредитация может вернуть `NULL`;
- `valid_until` для СГР остаётся `NULL`.

Статусы документа: `Действителен`, `Приостановлен`, `Прекращен`. Старое значение `Отозван` мигрирует в
`Прекращен`. Один реестровый документ может существовать только один раз, поэтому уникальна пара
`(document_type, title)`. Внешний идентификатор уникален в пределах типа документа: `(document_type, external_id)`.
`title` остаётся номером документа. После успешной синхронизации `name` строится из номера и дат в формате
`НОМЕР от ДД.ММ.ГГГГ до ДД.ММ.ГГГГ`; при отсутствии даты окончания используется формат
`НОМЕР от ДД.ММ.ГГГГ`.

Создаётся справочник `technical_regulations` с уникальными nullable `fsa_id`, обязательным уникальным `doc_num` и
nullable `name`. M:N хранится в `document_technical_regulations` с уникальной парой
`(document_id, technical_regulation_id)`.

Текстовое поле `technical_regulation` удаляется из метаданных. Физическая legacy-колонка сохраняется на один этап
миграции для безопасного rollback и не используется runtime-кодом.

## Слои и сервисы

```text
interfaces (hooks, HTTP action, queue, cron)
                  |
                  v
application (full synchronization, status check, schedule due)
                  |
                  v
domain (statuses, normalized document, SGR TR parser, invariants)
                  ^
                  |
infrastructure (FSA/EAEU clients, NocoBase repository, clock, queue adapter)
```

- `FsaRegistryClient` выполняет login, кэширует Bearer только в памяти, повторяет авторизацию после `401` и не
  журналирует учётные данные или токен.
- FSA, ЕАЭС и SWIS имеют отдельные gateway-адаптеры и общий нормализованный результат.
- FSA NSI вызывается только для отсутствующих локально `fsa_id`.
- Полная FSA-карточка используется только полной синхронизацией. Ежедневная проверка читает ID и статус из точного
  поискового результата и не вызывает detail endpoint или FSA NSI.
- Для СС и ДС, номер которых содержит код страны `KG` (`KG 417` или `KG417`), composite gateway выбирает SWIS
  вместо FSA. Полная синхронизация читает основные данные из HTML-таблицы `reportTable` соответствующего реестра,
  затем получает ТР из `/Doc/{UUID}`. Облегчённая ежедневная проверка ограничивается первой HTML-страницей.
- Репозиторий выполняет upsert ТР под уникальными ограничениями и атомарно заменяет M:N-набор документа.
- HTTP action «Проверить сейчас» использует то же object-level право, что и `update` документа.
- HTTP action ручной проверки ожидает окончательный результат use case; после ответа клиент вызывает штатный
  `useDataBlockRequestGetter().getDataBlockRequest().refreshAsync()` текущего data block. Первичная проверка запускается
  middleware только после успешного действия `permit_documents:create`, а повторная — после успешного
  `permit_documents:update`, если сохранённые номер или тип действительно изменились. Запрос не выполняется при простом
  редактировании поля до Submit. Ежедневная проверка продолжает использовать очередь.

## Алгоритм первичной синхронизации

1. `beforeCreate` устанавливает `PENDING`; при смене `title` или `document_type` также очищаются внешний ID и старые
   реестровые значения, а `name` временно получает номер документа.
2. После успешного Submit middleware повторно читает актуальную идентичность документа и запускает полную
   синхронизацию до формирования ответа API.
3. Ручное действие «Проверить сейчас» запускает тот же полный сценарий.
4. При отсутствии `external_id` выполняется точный поиск по `title`; при наличии ID сразу запрашивается карточка.
5. Временные сетевые ошибки повторяются до трёх попыток с backoff. Исчерпание попыток даёт `ERROR` без удаления ранее
   корректных данных.
6. Поиск без результата даёт `NOT_FOUND`. Для новой идентичности реестровые поля и связи остаются пустыми.
7. Ответ нормализуется и проверяется. Для ДС/СС `product_information` формируется только из всех непустых
   `product.identifications[].name`; `product.fullName` не используется. Неполная карточка даёт `ERROR`.
8. Неизвестные FSA ТР разрешаются одним запросом `/nsi/api/multi`; СГР ТР разбираются из `DOC_GIGHARK_NAME`.
9. В одной транзакции повторно проверяется неизменность `title`/`document_type`, выполняется upsert ТР, синхронизация
   M:N, расчёт `name` и обновление документа в `SUCCESS`.

## Периодическая и ручная проверка

- Cron запускается в `00:00` по `Asia/Vladivostok`.
- `TODAY` для API СГР вычисляется по календарю `Europe/Moscow`.
- Ежедневно документы `SUCCESS` и документы `ERROR` с сохранённым `external_id` проходят облегчённую проверку:
  выполняется точный поиск по номеру, проверяется совпадение внешнего ID и обновляются только `status`,
  `external_status`, `sync_status`, `last_checked_at` и `last_sync_error`.
- `PENDING` и `ERROR` без `external_id` проходят полную синхронизацию, поскольку для них ещё нельзя ограничиться
  обновлением статуса.
- `NOT_FOUND` автоматически не повторяется: новый поиск начинается после смены номера/типа или действия
  «Проверить сейчас».
- Повторные ручные запросы для одного документа присоединяются к уже выполняемой полной синхронизации и получают один
  окончательный результат без дублирования запроса к реестру.
- Незавершённые `PENDING` восстанавливаются при запуске приложения.
- Если набор ТР не изменился, строки M:N повторно не записываются.

## Конфигурация и безопасность

Обязательные production-переменные: `FSA_USERNAME`, `FSA_PASSWORD`. Опционально можно переопределить фиксированные
base URL через `FSA_BASE_URL`, `EAEU_BASE_URL` и `SWIS_BASE_URL`. Секреты не хранятся в Git, БД, сообщениях ошибок или
логах.
