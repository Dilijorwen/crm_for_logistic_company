# Рефакторинг зависимостей Log Company

## Область и сохранение поведения

Проверены собственные плагины CRM по графу проекта и связанным исходникам. Upstream NocoBase рассматривается только как интеграционная граница. Публичные API, UI, сообщения, правила доступа и схема данных сохраняются. Дополнительная чистка комментариев и удаление тестов исключены пользователем.

До изменений сохранены `git status` и diff в `/tmp/log-company-untangle-baseline-*`. Незавершённые пользовательские изменения `plugin-process-governance` для нескольких китайских клиентов поставки не относятся к этому рефакторингу. Их не откатываем и не включаем в развёртывание.

## Решения над подтверждёнными проблемами

### 1. Единое определение поставки для встраиваемых блоков

- `plugin-process-documents/src/client/widgets/process-documents/model/useProcessTarget.ts` и `plugin-process-discussion/src/client/widgets/process-discussion/ui/ProcessDiscussionBlock.tsx` содержат практически одинаковое разрешение контекста: form records, collection filter key, popup model, nested route, explicit props.
- Изменение приоритета одного источника приходится вручную повторять в другом блоке.
- Общий hook будет принадлежать `plugin-process-governance`, от которого уже зависят оба блока. Существующие exports, props, статусы и порядок источников сохраняются.
- Повторный `export * from './shared/lib'` в клиентской точке входа governance и повторный named export `getInnermostRouteFilterByTk` удаляются без изменения набора экспортов.

### 2. Пункт меню хранит своё действие

- `EmployeeListItem.tsx` и `DepartmentCard.tsx` отдельно объявляют пункты меню и таблицу обработчиков с теми же строковыми ключами.
- Обработчик задаётся рядом с пунктом. Порядок, разделители, labels, danger и доступность пунктов сохраняются.

### 3. Общее связывание действий сотрудника с правами

- `DepartmentCard.tsx` повторяет ACL и привязку callbacks для руководителя и участника; аналогичный код находится в `DetailsModals.tsx` и `EmployeeSidebar.tsx`.
- Общая функция связывает только переданные действия с прежними проверками прав. Вызывающий компонент продолжает определять допустимые для своего контекста действия.
- Руководитель не получает make-manager. В sidebar назначение доступно неназначенному сотруднику, перемещение — назначенному; выбор отдела не меняется.

### 4. Единый путь владельца документов в хранилище

- `UploadProcessDocuments.ts` задаёт `shipments/<id>` / `shipments/drafts/<token>`; `DeleteProcessDocumentsForProcess.ts` независимо восстанавливает `shipments/<id>/` для поиска оставшихся объектов.
- Один чистый helper связывает создание ключей и очистку. Точные значения, trailing slash для prefix, порядок транзакций и компенсация остаются прежними.

## Сохраняемые специальные случаи

- Контексты legacy form, FlowModel popup и вложенного маршрута нужны для уже существующих вариантов размещения блоков. Их приоритет фиксируется тестами; fallback optional methods не удаляется без замены совместимости.
- Отдельные состояния `new`, `missing`, `loading` определяют разные UI-сценарии и не объединяются.
- Chat selectors и organization selectors используют разные API/правила поиска; общий диалог создал бы ненужную связь.
- Доступность действий зависит от роли сотрудника в конкретном окне, а не только от глобальных ACL.
- Загрузка компенсирует откат удалением новых объектов; удаление поставки очищает хранилище после commit. Это различающиеся жизненные циклы, не кандидаты на объединение.
- Public barrels и совместимые exports сохраняются там, где на них опирается загрузчик NocoBase или внешние consumers.

## План проверки

1. Добавить тесты текущего поведения перед переносом логики, затем выполнить целевые тесты каждого изменения.
2. Проверить client/server/domain types и архитектурные границы FSD/Onion.
3. Выполнить ESLint с `--fix`, форматирование затронутых файлов, `git diff --check` и сборку затронутых плагинов.
4. Повторить независимый аудит субагентами; исправить обоснованные остаточные связи в области задачи.
5. Выполнить `graphify update .`, проверить итоговый diff и сохранность исходных пользовательских изменений.

Результаты проверок будут добавлены по фактическому выполнению.
