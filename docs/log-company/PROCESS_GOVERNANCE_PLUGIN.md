# Рейсы, поставки и история изменений

Плагин `@log-company/plugin-process-governance` переводит таможенное оформление с учёта одной машины на модель
«рейс — поставка». Исходники плагина в `packages/plugins/@log-company/plugin-process-governance` являются единственным
источником истины. Установленная копия в `storage/plugins` формируется только штатной сборкой и установкой NocoBase.

## Модель данных

### `vehicles`

- `id` — системный snowflake ID;
- `registration_number` — глобально уникальный нормализованный номер автомобиля.

Пользователь не выбирает автомобиль из справочника. При сохранении рейса сервер нормализует введённый номер, находит
существующий автомобиль или атомарно создаёт новый. Применяются NFKC, верхний регистр, удаление только пробельных
символов и замена визуально совпадающих кириллических букв `АВЕКМНОРСТУХ` на латинские. Печатные спецсимволы,
включая `/`, дефис и точку, сохраняются как часть номера. Итоговый формат: от 2 до 32 печатных ASCII-символов;
буквы неподдерживаемых алфавитов отклоняются проверкой.

### `transport_runs`

- `id` — системный snowflake ID;
- `run_number` — неизменяемый отображаемый порядковый номер;
- `status` — необязательный для ручного заполнения статус; если его не указать, сервер присваивает `queue`;
- `vehicle_id` — обязательная ссылка на `vehicles`;
- `departure_city_id` — необязательный город отправления;
- `managers` и `declarants` — необязательные связи многие-ко-многим с пользователями;
- `parent_runs` / `child_runs` — направленный граф связей между рейсами;
- `shipments` — связь многие-ко-многим с поставками;
- стандартные `createdAt`, `createdBy`, `updatedAt`, `updatedBy`.

`run_number` выдаётся PostgreSQL sequence. Удаление рейса не перенумеровывает оставшиеся записи и не удаляет поставки.
Рейс может быть сохранён без поставок, менеджеров и декларантов. Самоссылки и циклы в графе рейсов запрещены сервером;
проверка защищена транзакционной advisory-блокировкой PostgreSQL.

### `shipments`

- `id` — системный snowflake ID;
- `shipment_number` — неизменяемый отображаемый порядковый номер;
- `display_name` — автоматически вычисляемое составное название;
- ровно один обязательный китайский клиент через `chinese_client_id`;
- ровно одна обязательная наша компания через `company_id`;
- необязательный контракт, который обязательно должен быть связан с выбранной нашей компанией через
  `importer_contracts`;
- все поля таможенного оформления, НТМ, СВХ, инвойса и комментария менеджера;
- `runs` — связь многие-ко-многим с рейсами;
- `comments` — связь с `shipment_comments`;
- стандартные `createdAt`, `createdBy`, `updatedAt`, `updatedBy`.

`shipment_number` — глобальный номер поставки, поэтому он не зависит от рейса и не меняется при прикреплении к другому
рейсу. `display_name` формируется сервером по шаблону
`shipment_number/клиент/номер инвойса/номер ЗВ/номер ДТ`; отсутствующая часть заменяется на `—`. Поле нельзя вводить
вручную, оно создаётся для любого способа добавления поставки, обновляется после изменения поставки или имени клиента
и используется как `titleField` коллекции.

Внутренний `shipment_number` и внешний `route_delivery_number` имеют разные назначения. Одна поставка может
одновременно входить в несколько рейсов. Удаление связанной поставки блокируется с сообщением: `Нельзя удалить
поставку, пока она связана с рейсами. Удалите связанные рейсы или уберите поставку из них.`

Поле «Контракт» в стандартной форме NocoBase фильтруется по полю «Наша компания». При смене компании список
контрактов пересчитывается, а сервер дополнительно отклоняет сохранение контракта другой компании. Связанные объекты
`chinese_client`, `company`, `contract_record` и `customs_warehouse`, полученные из стандартной формы NocoBase,
проецируются в физические внешние ключи до обязательной ORM-валидации. Форма поставки может только выбрать
существующую связанную запись по ID: переданные вместе с выбором названия и другие поля справочника не обновляются
из формы поставки.

Все числовые поля поставки типа `double` принимают и запятую, и точку как десятичный разделитель: `1,0` и `1.0`
сохраняются как одно и то же значение `1`. Правило применяется стандартными полями NocoBase, временной формой плагина
и повторно проверяется сервером для прямых API-запросов. Отрицательные, бесконечные и неоднозначные значения с двумя
разными разделителями отклоняются с сообщением о неверном формате.

В справочниках `chinese_clients` и `our_companies` зарегистрировано обратное поле `shipments` типа `hasMany`. Оно
использует тот же внешний ключ поставки (`chinese_client_id` или `company_id`) и позволяет добавлять в карточку клиента
или компании стандартный связанный блок «Поставки». Устаревшие обратные association-поля этих справочников,
нацеленные на `customs_processes`, удаляются из метаданных; строки справочников и поставок при этом не изменяются.

Поля `createdAt` и `updatedAt` зарегистрированы в метаданных конструктора под русскими названиями «Дата создания» и
«Дата обновления». У неизменяемых журналов `transport_run_history` и `shipment_history` доступна только дата создания:
даты обновления у append-only записей намеренно нет. Поля дат добавляются в существующие ACL-разрешения просмотра
менеджера, декларанта и финансиста без удаления уже настроенных разрешённых полей.

## Таблицы связей

| Таблица | Назначение | Уникальная пара |
| --- | --- | --- |
| `transport_run_shipments` | рейсы ↔ поставки | `transport_run_id`, `shipment_id` |
| `transport_run_managers` | рейсы ↔ менеджеры | `transport_run_id`, `user_id` |
| `transport_run_declarants` | рейсы ↔ декларанты | `transport_run_id`, `user_id` |
| `transport_run_parent_links` | граф рейсов | `child_run_id`, `parent_run_id` |

Такая схема соответствует 3НФ: машина, рейс, поставка, пользователь и история не дублируют данные друг друга, а связи
многие-ко-многим вынесены в отдельные таблицы.

## Автоматическая история

История хранится отдельно:

- `transport_run_history` — история рейса;
- `shipment_history` — история поставки.

Обе таблицы append-only: ручные `create`, `update` и `destroy` запрещены HTTP pre-action, а прямые `create` и `update`
дополнительно блокируются database hooks. Внутреннее каскадное удаление истории разрешено только вместе с удалением
родительского рейса или поставки. Запись содержит тип события, техническое имя и отображаемую подпись поля, старое и
новое значение, время и пользователя. Для рейсов и поставок используется один и тот же полный аудит
бизнес-полей. Повторные ORM-хуки одного сохранения не перезаписывают исходный снимок, поэтому
одновременное изменение нескольких полей и связей фиксируется без потерь. Пишутся события:

- создание записи;
- начальное значение каждого заполненного бизнес-поля при создании;
- изменение любого бизнес-поля;
- добавление и удаление менеджера, декларанта или родительского рейса;
- прикрепление и открепление поставки.

Изменение связи рейс–поставка отражается с обеих сторон: в истории рейса появляется поставка, а в истории поставки —
рейс. Связь родительского и дочернего рейса также отражается в истории обоих рейсов. Системные ID, служебные timestamps,
вычисляемое название и неизменяемые номера не дублируются как изменения полей.

История — это журнал изменений текущей сущности. При удалении самой сущности её дочерняя история удаляется каскадно;
удаление рейса при этом не затрагивает поставки и их историю.

## Интерфейс

Четыре основные коллекции доступны в конструкторе NocoBase как самостоятельные детали интерфейса:

- `transport_runs` — «Рейсы»;
- `shipments` — «Поставки»;
- `transport_run_history` — «История рейсов»;
- `shipment_history` — «История поставок».

Служебные коллекции машин, комментариев и таблицы связей скрыты из списка коллекций конструктора. Они продолжают
работать через поля связей основных коллекций и серверную бизнес-логику. В коллекции рейсов технические поля
`vehicle` и `vehicle_id` также скрыты: в таблицах и формах используется только одно поле `Номер машины`
(`registration_number_input`). При чтении сервер заполняет его из связанной записи `vehicles`, а при сохранении
находит существующую машину или создаёт новую.

Создание, просмотр, редактирование и удаление настраиваются стандартными действиями NocoBase. Для связи
рейс–поставка используются стандартные действия блока связи: добавление новой записи, прикрепление существующей и
открепление. «Открепить» удаляет только связь; стандартное удаление поставки удаляет саму поставку и блокируется, пока
она связана хотя бы с одним рейсом.

Форма рейса передаёт связь `shipments` на сервер только как список идентификаторов. Даже если стандартный клиент
NocoBase сохранил в состоянии формы полные объекты строк, сервер отбрасывает их вложенные поля и не позволяет
устаревшему снимку перезаписать только что изменённую поставку. После успешного сохранения поставки связанные блоки
рейсов и таблица связи перечитываются из API. Это синхронизирует составное название и остальные отображаемые данные
без перезагрузки страницы. Состояние формы поставки помечается сохранённым только после завершающего post-save refresh:
guard закрытия не видит промежуточное dirty-состояние, а реальные изменения, сделанные без сохранения, по-прежнему
вызывают предупреждение.

Редактирование родителей выполняется стандартным полем `parent_runs`; сервер запрещает самоссылки и циклы.
Модуль также предоставляет блок и действие записи «Дерево рейсов» для `transport_runs`. Блок показывает родителей
выше дочерних рейсов, подсвечивает текущий рейс и повторяет общих потомков в каждой ветке. Отдельный плагин дерева
процессов для этого больше не требуется. Нажатие на другой рейс открывает его карточку в той же ветке интерфейса;
карточка текущего рейса неактивна.

Новый логистический интерфейс пишется непосредственно на русском языке и не использует i18n. Готовая страница с
жёсткой компоновкой не является основой модуля: рабочие страницы собираются пользователем из коллекций, полей, блоков и
действий в конструкторе NocoBase.

Блоки `Обсуждение поставки` и `Документы поставки` добавляются в popup записи `shipments`. Они не принадлежат рейсу и
не требуют номера машины. Удаление поставки каскадно удаляет её обсуждение и новые документы после того, как поставка
будет откреплена от всех рейсов.

Временная тестовая страница «Таможенное оформление» на `/admin/customs-clearance` пока сохранена для проверки сценария.
Её модальное окно рейса содержит вкладки:

1. «Рейс» — номер машины, статус, город, менеджеры, декларанты и связанные рейсы;
2. «Поставки» — добавление новой или существующей поставки, открытие, редактирование и открепление;
3. «История» — неизменяемый журнал рейса.

При создании вкладки поставок и истории недоступны до первого сохранения. Кнопка «Создать и перейти к поставкам»
сохраняет рейс, оставляет окно открытым и переключает его на поставки. У формы поставки есть вкладки общих данных,
таможенного оформления, НТМ и истории (для уже созданной записи).

Клиент скрывает или блокирует действия по ACL, но окончательное решение всегда принимает сервер.

## Права

- `manager` и `declarant`: просмотр/создание/изменение рейсов и поставок, просмотр истории, работа с комментариями;
- `financier`: просмотр рейсов и истории, изменение разрешённых финансовых полей поставки;
- ручное изменение истории запрещено для всех ролей, включая ошибочно выданные ACL-разрешения;
- удаление доступно только роли, которой явно выдано действие `destroy` в NocoBase.

Ограничения на изменение отдельных статусов по ролям из прежней модели не переносятся: статус теперь является полем
рейса и подчиняется обычному ACL ресурса `transport_runs`.

## Миграции и совместимость

Миграции создают коллекции, sequence, уникальные индексы, физические внешние ключи, проверки допустимых значений,
отложенные ассоциации с пользовательскими справочниками, обратные связи поставок, русские метаданные системных дат,
ACL и новый маршрут страницы. Обратные миграции намеренно не удаляют таблицы с пользовательскими данными и не
ослабляют ограничения целостности.

NocoBase 2.0.60 при поздней синхронизации коллекций удаляет пользовательские unique-индексы, даже если они объявлены в
статической коллекции. Поэтому после `afterStart` плагин идемпотентно проверяет и восстанавливает три индекса:
`vehicles.registration_number`, `transport_runs.run_number` и `shipments.shipment_number`. Сервер считается готовым
только после успешного завершения этой проверки.

Прежние `customs_processes`, `process_history` и связанные документы не удаляются и не переносятся автоматически. Это
позволяет сохранить существующие записи и выполнить отдельный контролируемый перенос после согласования правил
сопоставления старого процесса с рейсом и поставкой.

## Сборка и установка

Из корня репозитория:

```bash
yarn eslint --fix packages/plugins/@log-company/plugin-process-governance/src
yarn build @log-company/plugin-process-governance
yarn tar @log-company/plugin-process-governance
docker compose exec -T app yarn pm add /app/nocobase/storage/tar/@log-company/plugin-process-governance-<version>.tgz
docker compose exec -T app yarn nocobase upgrade
docker compose restart app
```

Если модуль уже установлен, используйте `yarn pm update` с новым tarball вместо `yarn pm add`; это обновляет версию
плагина в реестре NocoBase.

После обновления необходимо дождаться сообщения `app has been started`, открыть страницу под авторизованным
пользователем и проверить ACL нужных рабочих ролей.
