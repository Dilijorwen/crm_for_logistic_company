# Поиск по текущей коллекции

Плагин `@log-company/plugin-collection-search` добавляет универсальный поиск по текущей коллекции
NocoBase. Он не привязан к странице, имени коллекции или конкретной кнопке.

## Возможности

- поиск подстроки сразу по всем поддерживаемым полям текущей коллекции;
- поиск по всей коллекции независимо от фильтров открытого блока;
- поддержка строк, многострочного текста, чисел, дат, логических полей и подписей вариантов выбора;
- исключение первичных ключей, внешних ключей, паролей, файлов и связей;
- учёт разрешений NocoBase на записи и поля;
- подсветка совпавшей части значения;
- группировка найденного по полям;
- серверная пагинация;
- задержка 350 мс после ввода;
- интерфейс на русском и английском языках.

Минимальная длина запроса — 3 символа. Например, запрос `628` одновременно найдёт `628` в
номере машины, номере ДТ, номере ЗВ и других доступных полях.

## Подключение в интерфейсе

### Готовая кнопка

В режиме настройки страницы:

1. Откройте меню добавления действия в блоке нужной коллекции.
2. Выберите действие **Поиск**.
3. Сохраните схему.

Кнопка сама откроет диалог поиска и возьмёт коллекцию из контекста блока.

### Уже созданная popup-кнопка

Для существующей кнопки на странице «Таможенные оформления»:

1. Откройте созданный кнопкой диалог в режиме настройки.
2. Нажмите добавление блока в пустой области диалога.
3. Выберите **Другие блоки → Поиск по текущей коллекции**.
4. Сохраните схему.

Блок возьмёт `customs_processes` из `current collection`. Этот же способ работает в любом другом
диалоге, где NocoBase передаёт контекст коллекции.

## Устройство и производительность

Проект использует PostgreSQL 16. Плагин создаёт расширение `pg_trgm`, отдельный поисковый документ
для каждой записи и GIN trigram-индекс по объединённому поисковому тексту. Поэтому запрос не
строит длинный `OR` с последовательным просмотром каждого столбца исходной таблицы.

Индекс текущей коллекции строится лениво при первом поиске. На пустой или небольшой коллекции это
почти незаметно. Для сотен тысяч или миллиона записей первоначальная подготовка может занять от
десятков секунд до нескольких минут в зависимости от размера полей, диска и нагрузки. Во время
подготовки интерфейс показывает состояние загрузки. После подготовки создание, изменение и
удаление записей синхронно обновляют поисковые документы.

Обычный запрос после построения индекса должен выполняться за десятки или сотни миллисекунд.
Точное время зависит от частоты запроса, количества доступных пользователю записей, размера
поискового документа и ресурсов PostgreSQL. Особенно общий запрос может быть медленнее точного
номера, поскольку он создаёт больше кандидатов.

Контрольный локальный тест PostgreSQL 16.14 на 1 000 000 синтетических поисковых документов дал:

- создание GIN-индекса — 16,98 с;
- общий запрос `628`, возврат первых 200 кандидатов — 14,81 мс на уровне БД;
- точный фрагмент номера, один кандидат — 2,75 мс на уровне БД.

Это не SLA: полное время API дополнительно включает ACL-проверку и чтение исходных записей, а
первичное индексирование через приложение зависит от количества и размера реальных полей.

## Безопасность

Поисковый индекс используется только для отбора кандидатов. Перед возвратом результата плагин
повторно читает исходную коллекцию через репозиторий NocoBase:

- добавляет ACL-фильтр текущего пользователя;
- запрашивает только разрешённые поля;
- отбрасывает недоступные записи;
- вычисляет и возвращает совпадения только по разрешённым полям.

Текущие пользовательские фильтры таблицы намеренно не применяются — поиск выполняется по всей
доступной пользователю коллекции.

## Ограничения

- Поддерживается PostgreSQL с доступным расширением `pg_trgm`.
- Связи и файлы не индексируются: их представление может находиться в других коллекциях и иметь
  отдельные ACL-правила.
- После изменения состава или типа полей поисковый документ коллекции перестраивается при
  следующем запросе.
